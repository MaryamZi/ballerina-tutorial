# Ballerina tutorial

A tour of Ballerina through thirteen small samples — from a first HTTP client to a Kafka consumer, with data mapping, resilience, connectors, databases, code-gen, an isolated service, and tests along the way. Every sample can be run standalone; each has its own README.

## Samples

| # | Sample | What it shows |
|---|---|---|
| 01 | [`01-client`](01-client) | Fetch a single order and bind the response to a typed record. The minimal HTTP client call. |
| 02 | [`02-json-and-xml`](02-json-and-xml) | The same fetch as sample 1, with the response typed as raw `json`; a second variant fetches XML from a customers backend. |
| 03 | [`03-generated-client`](03-generated-client) | The same fetch as sample 1, with the HTTP client and record types code-generated from an OpenAPI spec. |
| 04 | [`04-resilience`](04-resilience) | HTTP client with `retryConfig`. Talks to a flaky backend that fails N times before succeeding. |
| 05 | [`05-mapper`](05-mapper) | Two data-mapper transformations — one-to-one field mapping and multi-source join. HTTP-free. |
| 06 | [`06-connector`](06-connector) | Send an email via the `ballerinax/googleapis.gmail` connector, pointed at a local Gmail mock. |
| 07 | [`07-database`](07-database) | Read a row from Postgres via `ballerinax/postgresql` and `sql:ParameterizedQuery`. Extended CRUD service in the README. |
| 08 | [`08-persist`](08-persist) | The same read as sample 7, but the data access client is code-generated by `bal persist` from a record model. |
| 09 | [`09-automation`](09-automation) | Full flow — read (client) → map (mapper) → POST summaries to a reports backend. |
| 10 | [`10-service`](10-service) | Expose an HTTP service — GET list with a category filter, GET by id, POST to create. |
| 11 | [`11-service-isolated`](11-service-isolated) | Sample 10 with `isolated` + `lock` blocks — the isolation warnings go away, resources can run concurrently. |
| 12 | [`12-events`](12-events) | Kafka consumer service — typed payload binding on each incoming record. |
| 13 | [`13-tests`](13-tests) | A small `/summaries` service exercised at three layers — pure mapper test, mocked-client test, and service test with an `http:Client`. |

## Mock backends

`backends/` holds services the samples talk to:

- `backends/orders` — orders (port 9090). `GET /orders?date=YYYY-MM-DD` list, `GET /orders/{orderId}` single. JSON.
- `backends/reports` — accepts summaries (port 9091). `POST /reports/summaries` logs each summary. Used by sample 9.
- `backends/customers` — customers (port 9096). `GET /customers` list, `GET /customers/{customerId}` single. **XML**, used by sample 2.
- `backends/flaky` — flaky endpoint (port 9097). `GET /flaky/orders` returns 503 twice then 200. Used by sample 4.
- `backends/gmail-mock` — Gmail impersonator (port 9092). Used by sample 6.

Start each with `bal run` from its directory. Only start the ones the sample you're running needs.

## Prerequisites

- Ballerina 2201.13 or later — check with `bal version`.
- VS Code with the Ballerina extension.
- `docker compose` for samples 7, 8 (Postgres) and 12 (Kafka).
- [`hurl`](https://hurl.dev/) for driving samples 10 and 11 (optional — `curl` also works).

## Running a sample

Each sample's `README.md` lists the specific backends, config, and commands. General pattern:

```
# terminal 1 — start any backends the sample needs
cd backends/orders && bal run

# terminal 2 — run the sample
cd <sample-dir>
bal run
```
